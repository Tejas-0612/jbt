# CLAUDE.md — Job Application Tracker (JBT)

## What we're building
A candidate-first personal job-search tracker ("a personal operating system for a job search").
Core promise: **know every application, understand what happened, and know what to do next.**
The **Application** is the central object. Timeline, follow-ups, interviews and notes all hang off it.
Target: **real public users** (after the MVP proves itself; see "Before public launch").

State (2026-10-24): **Phase 0 done** (steps 1–9: workspace, Docker, Fastify API, Prisma, web app, `packages/shared`, web tests, CI on GitHub via PR #1, README). **Slice 1 (Create Application) done** (PR #2, merged 2026-10-24). Every slice: one branch + one PR, one commit per step; the user pushes and opens the PR after the last step. Slice 1 decisions: stand-in signed-in user = one small Fastify hook (seeded user A; tests can pick B; services take `userId`; real login later replaces only that hook; off in production → 401). Lean fields: company, role title, status (default APPLIED), `appliedOn` (required unless SAVED, empty for SAVED, not in the future in the user's timezone) + optional job URL (http/https only), location, work mode, job description. Creation = one `STATUS_CHANGED` activity with `fromStatus` null, dated `appliedOn` when created as APPLIED, otherwise the moment it was saved. The "follow up in 7 days" offer waits for the follow-ups slice. Steps: **1a** (schema, first migration, seed, DB tests) done and committed; **1b** API (`POST /api/v1/applications`, `GET /api/v1/applications/:id`, shared Zod schemas, service, stand-in hook, `@date-fns/tz`) done and committed. A backdated APPLIED event is dated **noon** of `appliedOn` in the user's timezone (survives a later timezone change and DST midnight gaps); applied today → the real moment. **1c** web (app shell, dashboard placeholder, `/applications/new` form, bare `/applications/:id` page; the temporary system-status page is deleted) done and committed. 1c decisions (user, 2026-10-24): native `<select>`s and the browser's own date input for now (custom dropdown / calendar popover maybe later, e.g. with follow-up presets); the form is a full page ("let's see how it goes"); the nav shows only pages that exist (Dashboard; mobile tabs Home + Add). **Slice 2 (sign in with Google) in progress** on branch `slice-2-google-login`. Decisions (user, 2026-10-24): server-side authorization-code flow with `openid-client` 6.8.8 (state + PKCE + nonce + ID-token checks) and `@fastify/cookie` 11.1.3; scopes `openid email profile` only, and Google's own tokens are thrown away after sign-in. Users are found by `googleSub`; email and name are refreshed at every sign-in; `email_verified` is required; the timezone comes from the browser at first sign-in (invalid → UTC); two first sign-ins at once → catch `P2002`, retry once. **Sessions:** a random 32-byte token in an HttpOnly cookie (`jbt_session`, `__Host-jbt_session` + Secure in production, SameSite=Lax, Path=/); only its SHA-256 is stored in `sessions`; **sliding 30-day expiry**, renewed at most once a day (re-send the cookie when renewed); sign-out sets `revokedAt` (rows kept); every sign-in gets a new token. ## Settled: foundations (from the docs/ADRs)
- Modular monolith. Node.js + TypeScript API, React + TypeScript + Tailwind web app.
- PostgreSQL is the source of truth. Prisma with committed migrations.
- REST under `/api/v1`. Envelopes: `{ data, meta }` and `{ error: { code, message, details } }`.
- Google OAuth only (no passwords).
- Ownership is enforced in the backend on every query (`WHERE id = ? AND userId = ?`). Never trust a client-sent userId.
- Status changes and their timeline entry are written in one transaction.
- Timestamps are stored in UTC and shown in the user's timezone.

## Settled: 2026-10-17 review decisions
**Product**
- Application statuses: `SAVED, APPLIED, SCREENING, INTERVIEWING, OFFER, ACCEPTED, REJECTED, WITHDRAWN, GHOSTED`.
- **Next action** = the application's earliest pending follow-up or upcoming interview.
- **Needs attention** (dashboard): follow-ups overdue or due today; interviews today/tomorrow; past interviews still `SCHEDULED` → "How did it go?"; active applications (APPLIED/SCREENING/INTERVIEWING) with no activity for 14 days and no pending follow-up → "Follow up or mark as ghosted".
- On create with status APPLIED: offer "Remind me to follow up in 7 days" (on by default). The user can change it to any custom date/time.
- Reminders: one daily digest email (user's local morning) plus an optional custom reminder time per follow-up. No in-app notification center in MVP.
- Store the pasted job description on the application.
- MVP navigation: Dashboard, Applications, Agenda (Overdue / Today / This week), Settings.
- CSV import comes right after the core slices.

**Data model**
- No `Role` table. Role fields live on `Application`. `Company` is required, found or created by name (per user) inside `POST /applications`.
- `userId` on every user-owned table, with cascade delete from `User` (makes account deletion and export cheap later).
- `appliedOn` and follow-up `dueDate` are DATE. Follow-up `remindAt` is an optional timestamp. Interview `scheduledAt` is a timestamp.
- `User.timezone` (IANA, read from the browser at first login) and `User.googleSub` (unique; identify users by it, not email).
- Status history: `Activity` has `fromStatus`/`toStatus` columns. `occurredAt` can be backdated. A status change is exactly one `STATUS_CHANGED` activity.
- Timeline = things that happened (dated). Notes = editable context. No `NOTE_ADDED` timeline events.
- Interview statuses: `SCHEDULED, COMPLETED, CANCELLED`. Rescheduling changes `scheduledAt` and logs an activity.
- Application `workMode`: `REMOTE, HYBRID, ONSITE` (optional; the design filters on it).

**Architecture**
- No Redis or job queue in MVP. The worker is a second start script in `apps/api` that polls Postgres every few minutes (digest + custom reminders, each marked as sent so they never repeat).
- Auth: plain HttpOnly session cookie backed by the `sessions` table. No JWT/refresh tokens. (User answered "no" to tokens; confirm if unsure.) CSRF: SameSite=Lax + `Origin` check on mutations.
- Web and API run on the same site (one custom domain, or `/api` proxied through the frontend host).
- Repo: pnpm workspace with `apps/web`, `apps/api`, `packages/shared` (Zod schemas used by both). No Turborepo or staging environment yet.
- Dev/test-only login: "Log in as…" a seeded sample user (at least two, so we can test that A can't see B's data). Disabled in production.
- Build order: Create Application first with a stub signed-in user, then real Google login.

**API conventions**
- Pagination `page`/`pageSize`. Another user's resource → 404 (no `APPLICATION_ACCESS_DENIED`). Validation errors → 400 `VALIDATION_ERROR`.
- Status changes go through `PATCH /applications/:id/status` only (not the general PATCH).
- Object storage is removed from the production checklists (file uploads are deferred).

**Lessons learned (don't repeat):**
- Vite's `loadEnv()` reading the root `.env` picks up `NODE_ENV=development` (meant for the API) and silently makes `vite build` a **development** build (`jsxDEV` in the bundle, +55% size, no warning). Read single values with `node:util` `parseEnv` instead.
- `pnpm -r --parallel` stops ALL apps when one exits; `pnpm dev` uses `--no-bail` so the web app survives an API crash.
- Visual checks without a browser window: headless Edge (`msedge --headless=new --screenshot=… --window-size=… --virtual-time-budget=8000 <url>`, then Read the PNG). For dark mode use only `--force-dark-mode`; `WebContentsForceDark` auto-inverts pages and hides whether our dark tokens work. The **first** screenshot right after `pnpm dev` starts can be blank (Vite still compiling the app for its first load): check with `--dump-dom` and take it again. Headless Edge can't go narrower than ≈ 500 px: `--window-size=390,…` lays out at ≈ 490 px and crops the picture, which looks like overflow. Check phone layouts at 500 px.
- New dependencies: check release dates (`pnpm view <pkg> time --json`) and prefer versions out for 2+ weeks; a same-day or few-days-old release (or a fresh major) waits. pnpm 12 saves versions exactly (`"7.89.0"`).
- `pnpm check` = typecheck + lint + format:check + test. Run it before every commit (tests need Docker).
- Stopping a background `pnpm dev` (TaskStop) on Windows leaves the Vite and tsx node processes running, holding ports 5173/4000. Find them by command line (`Get-CimInstance Win32_Process`) and stop only those PIDs.
- Vite's dev server listens on `::1` only: use `http://localhost:5173`, not `127.0.0.1:5173`.
- Test a database claim before stating it as fact: on 2026-10-22 Claude claimed `ON DELETE RESTRICT` would break a cascading user delete, and a throwaway-database demo (`CREATE DATABASE jbt_demo` in the container, then drop it) proved it wrong. `migrate diff --from-empty --to-schema <file> --script` shows a schema's SQL without touching any database.
- Prisma 7's `upsert` (with `update: {}`) runs `SELECT` then `INSERT`, not `INSERT … ON CONFLICT` (seen in the query log), so two simultaneous creates of the same unique row really collide: catch `P2002` and retry the transaction once. Two `Promise.all` requests through `app.inject` never collided in 3 runs, so a "concurrent" test proved nothing; stage the collision with a `$extends` query wrapper instead (`applications.test.ts`).
- Zod 4 runs an object's `superRefine` only when no field has an "aborting" problem (missing field, wrong type, bad enum); blank text (`min(1)`) and unknown keys don't abort, so a form's errors all show together.
- In Git Bash, paths from `node -p "require.resolve(...)"` come back Windows-style (`C:\…`); their backslashes get mangled and searches silently find nothing. `cd` into `node_modules/<pkg>` and use relative paths instead.
